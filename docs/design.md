# 设计说明

## 1. 硬件与原始链路

小米 Note Pro（leo）把有线耳机接在两条通路上：
- 普通通路：WCD9330 codec 自带的耳放。
- HiFi 通路：QUAT_MI2S 接口 → ESS ES9018（小米定制的 C2M 封装）→ 两级运放 OPA1612 和 ADA4896。

ES9018 是 I2S 的时钟主设备，板上有 45.1584 MHz 和 49.152 MHz 两颗晶振，分别对应 44.1 kHz 和 48 kHz 两个采样率族。

MoKee 原版的数据链路是：
1. 应用交出 44.1 kHz 的 PCM。
2. Android deep-buffer 混音器按 48 kHz 运行，**这里发生一次 44.1 → 48 的重采样**。
3. PCM 和 QUAT 后端都是 48 kHz。

混音器之所以固定在 48 kHz，有两个原因：音频策略 XML 为 deep_buffer 声明了 44100 和 48000 两个采样率，而 AudioPolicy 打开输出时会选其中最高的；HAL 的 deep-buffer 前端又用写死的 48000 覆盖了框架的请求。

## 2. 候选 A：共享后端的生命周期

QUAT 后端是共享资源，音乐（MultiMedia1）和提示音（MultiMedia5）可以同时使用它。原驱动每当一个使用者退出，就会重写后端配置并重置 HiFi 状态，结果是：提示音结束后，仍在播放的音乐被报告为空闲，而且在播放过程中被改写了后端。

候选 A 的做法：
- 按 usecase 和 stream 身份维护一个活动集合，重复的进入和退出都是幂等的。
- 只有第一个使用者进入、最后一个使用者退出时才允许写后端；其余时刻对后端只做读取确认。
- 恢复后端之前，必须先证明所有前端和设备路径都已关闭；恢复失败时保留"待恢复"状态。

## 3. 候选 B：44.1 kHz 同率

- 策略：deep_buffer 只声明 44100，于是混音器以 44.1 kHz 打开。
- HAL：deep-buffer 前端接受 44100 的请求，其他请求仍使用 48 kHz。
- 后端：采样率由**第一个**让 QUAT 设备进入工作的流决定，只允许 44.1 或 48，其他值一律回到 48。活动中的后端从不改时钟。最后一路退出时恢复为 48 kHz。
- 采样率不同的后来者（例如 48 kHz 的提示音）由高通 ADSP 重采样。这对提示音有影响，对音乐没有。
- 如果撤销策略覆盖，系统会回到 48 kHz 链路，不会出现 48 → 44.1 的反向重采样。

**已知限制**：这是固定 44.1 kHz 的原型。48 kHz 的音源会被转成 44.1 kHz。按音源自动切换采样率是下一阶段的工作。

## 4. 候选 C：DAC 硬件音量

目标：HiFi 工作时，Android 的增益固定为 0 dB，16 位样本原样到达 PCM；音量改由 ES9018 在内部以 32 位精度衰减。

- **DAC 刻度**：控件值 = 135 + 2 × 档位，对应 −60 + 档位（dB），档位 0～51，上限 −9 dB。原来 −25 dB 的固定值对应档位 35，作为默认值。
- **失败时变安静**：服务重启、最后一路退出、任何回读失败，都把 DAC 恢复到最安静的 −60 dB。
- **进入 HiFi 时恢复音量**：路由验证通过、但还没写入任何音频帧时，一次性写入保存的档位。档位保存在持久属性中，重启后保留。
- **保护开关 `hardvol`**：开启期间，HAL 在 `select_devices` 中拒绝普通耳机设备，返回 `-EPERM`，结果是没有声音。解除保护不需要会话身份，开启保护则需要当前会话。保护开关同样持久保存。
- **应用侧的顺序**：见 `app/hifi-controller/README.md`。

### 实测中发现并修复的问题

| 现象 | 原因 | 修复 |
|---|---|---|
| 正常关闭 HiFi 时，有一瞬间的大声 | 降低媒体音量后只隔 68 ms 就切换了通道，PCM/DSP 缓冲区里按 0 dB 混好的样本，从没有 DAC 衰减的普通耳放放了出来 | 恢复音量后先等 700 ms，再解除保护、切换通道 |
| 重启后硬音量被解除 | 开机时 HAL 默认 HiFi 关闭；应用恢复设置的中间状态，以及无障碍服务还没绑定的空窗期，都被误判为"离开 HiFi" | 忽略"请求进行中"的中间状态；判断服务是否开启时看系统设置，而不是看是否已绑定 |
| 每次重启后媒体音量变成 10/25 | Android 安全音量机制：开机时把耳机媒体音量限制在安全档位 | HiFi 激活时，若媒体音量不在最大值就重新设为最大 |

## 5. 测量方法

- **采样率链路**：依次核对 `dumpsys media.audio_flinger` 中的音轨 SRate 和混音线程采样率、`/proc/asound/card0/pcm0p/sub0/hw_params`、mixer 控件 `QUAT_MI2S SampleRate`、HAL 日志。
- **时钟**：用 `tools/device/rate.sh` 计算 PCM 硬件指针每秒推进的帧数。ES9018 是时钟主设备，所以这个数字就是实际的时钟族。实测结果：44.1 kHz 为 44,096～44,106 帧/秒，48 kHz 为 47,998.8～47,999.6 帧/秒。
- **并发**：用测试音源分别打开 MultiMedia1 和 MultiMedia5 两路，比较修复前后音乐的状态，以及后端控件被写入的次数。
- **安全**：用测试音源的 `raw-hifi-off` 命令模拟意外退出，确认 HAL 拒绝了普通耳机通道，并且应用随后的恢复顺序正确。

## 6. 已知问题

1. `dumpsys media.audio_flinger` 的输出如果被提前截断（例如管道接到 `grep -m1`），HAL 会因 SIGPIPE 退出，随后被系统自动重启。日常播放不会触发。尚未与原驱动对比，不确定是否是本项目引入的。
2. 音乐先停、提示音还在时，状态为 `hifi_active`，但 `live` 和 `flow` 都是 0。这种显示语义是否合适，尚未决定。
3. 意外退出后，正在播放的那一路会保持静音，要暂停再播放才能恢复。这是"宁可静音，不可变响"的取舍。
4. 重启后第一次播放的前 1 秒左右偏小声，原因是要等应用把被安全音量压低的媒体音量设回最大。
5. 比特完整没有测量证明，耳机口的输出电平也没有测量。
